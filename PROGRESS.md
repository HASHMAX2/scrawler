### Project Intelligence + hierarchy feature (major addition, superseded the earlier simple search)
A prior version of this session added a lightweight "combined search" (`GET /api/search`, LIKE-based, no persisted hierarchy). That has been **fully replaced** by a proper persisted project→building entity model per an explicit, detailed user spec. Summary:

- **Data model** (`ingestion/project_hierarchy.py`, `ingestion/warehouse.py`): new `dim_master_project` table + `master_project_id`/`building_label`/`building_slug`/`grouping_method` columns on `dim_project`. Grouping is **rule-based, never fuzzy** — `extract_building_suffix()` strips a trailing tower/building/phase number ("AZIZI VENICE 14" → master "azizi venice", building "14") or falls back to a hyphen-split for named sub-buildings ("Creek Beach - Canopy - Moor" → master "creek beach"). A `master_project_overrides` table (same pattern as the pre-existing `entity_alias_overrides`) lets a human correct any grouping; corrections persist across rebuilds. **Verified against real data**: all 16 "Azizi Venice N" towers correctly grouped into one master (`azizi-venice` slug), "Creek Beach" correctly grouped and flagged `needs_review` (hyphen-split method), 662 buildings grouped via trailing-number, 195 via hyphen-split, 2,369 stand alone as their own single-building master, 63 master groups flagged for review. `area_name`/`developer_name` on each master project are enriched post-hoc via `mode()` over the family's fact rows (e.g. Azizi Venice → area "Madinat Al Mataar", developer `None` since no scraped match exists — correctly not fabricated).
- **Search ranking** (`apps/api/analytics/search_rank.py`, pure + unit-tested): tiered exact-master > exact-building > alias-override > prefix > token-subset > fuzzy(rapidfuzz) ranking. Verified: searching "Azizi Venice" returns the master first, then all 16 buildings — matches the product spec's literal acceptance-test ranking example.
- **API**: `GET /api/search/suggest?q=` (autocomplete), `GET /api/projects/master/{slug}` (full Project Intelligence payload — KPIs incl. 30d/90d/6m counts & velocity, weekly trend series, unit-type performance, building comparison table, sales-vs-rentals derived stats, data-quality summary; supports `building_slug`/`unit_type`/`transaction_type` filters and `period` incl. new `"1y"`/`"all"` options). `explorer.py`'s sales/rentals endpoints gained `master_slug`/`building_slug` filters so the Project Intelligence page's recent-transactions/rentals tables reuse existing pagination rather than duplicating it. `data_quality.py` gained a `/project-hierarchy` review-queue endpoint and `/resolve-master-project` correction endpoint.
- **Frontend**: `ProjectSearchBar.tsx` rewritten as a real autocomplete combobox (debounced, arrow-key nav, Enter/Escape, loading/no-results states, localStorage recent searches) that **navigates** on selection rather than showing results inline (per explicit instruction). New `ProjectIntelligence.tsx` page at `/projects/:slug` and `/projects/:slug/buildings/:buildingSlug` — header, building-selector pill tabs ("All Buildings" + each tower), local period/unit-type/transaction-type filters, KPI row, 4 market-activity charts, unit-type performance table, sortable/searchable/clickable building comparison table, sales-vs-rentals stat cards, recent transactions/rentals tables, data-quality footer. ### Known issues fixed during in-browser testing (all applied)
1. Shared DuckDB connection across FastAPI's threadpool threads corrupted concurrent query results (`apps/api/db.py` hands out a `.cursor()` per request).
2. `uvicorn --reload` was watching the entire repo (incl. `node_modules`) — scoped to `--reload-dir apps/api --reload-dir ingestion`. **Even so, the file watcher has proven unreliable in this Windows/git-bash environment** — after several rapid edits it sometimes logs "Reloading..." and never actually swaps in the new code. When API changes don't seem to take effect, don't trust the reloader: kill node+python processes and run `npm run dev` fresh.
3. `fact_sales.canonical_bedroom` could be NULL (blank UI label) when `ROOMS_EN` was empty — coalesces to `"Unknown"`.
4. `dim_area` could contain two rows for the same community when raw DLD names differed only in case/punctuation (e.g. "Palm Deira" vs "PALM DEIRA") — fixed dedup in `build_dim_area`, verified zero duplicate `canonical_key`s.
5. **`PERIOD_DAYS` was missing a `"180d"` entry** (`apps/api/analytics/core.py`) — every route defaulting to `period="180d"` (project detail, developers list, decision engine) was silently falling back to a 30-day window instead. Fixed by adding the entry; regression-tested (`test_period_days_includes_180d`, `test_resolve_period_180d_uses_full_180_days`).
6. **Decision Engine score was double-scaling**: `weighted_sum = (weighted average, already 0-100) / available_weight * 100` — the trailing `* 100` pushed nearly every real result to the 100 cap, making the ranking meaningless. Extracted the score math into a pure, unit-tested `weighted_score()` function in `apps/api/analytics/core.py` (5 regression tests) and fixed `decision_engine.py` to use it. Verified live: scores now spread sensibly (e.g. 97.7, 93.4, ...) instead of clustering at 100.
7. Hot-project momentum ratio was unstable for near-zero trailing baselines (e.g. a project with 0.05 sales/month prior jumping to 3/month read as "6000% hot") — added a `MIN_BASELINE_MONTHLY = 1.0` floor in both `pulse.py` and `signals.py` before dividing.
8. **UX inconsistency**: `ProjectDetail.tsx` and `DecisionEngine.tsx` (the two newest pages) were not reading the global period selector from `useFilters()` — they silently used a hardcoded `period="180d"` regardless of what the top-right "Period" dropdown showed, unlike every other page. Fixed both to respect the global filter; verified in-browser (numbers now visibly change when switching 90D and confirmed distinct from the old 180d values).
9. Investigated an apparent mojibake (`â€”`) in API JSON responses containing em dashes — **turned out to be a false alarm**, purely a display artifact of piping `curl` through this Windows git-bash terminal. Verified at the byte level (source file bytes, in-memory Python codepoint, and raw HTTP response bytes all correctly show U+2014) and confirmed the browser renders it correctly. ## Propsearch crawler extension (`scraper/`) — separate effort, complete

A later session extended the existing Python/httpx/SQLite crawler (`scraper/`) rather than building a second system, per explicit instruction: target stays propsearch.ae only, mine a large "production property-graph crawler" spec for genuinely missing functionality, add only that. Full rationale/gap-analysis in the plan file `wobbly-napping-pelican.md`.

### Done
- **Politeness/compliance** (`scraper/fetcher.py`): `robots.txt` is now fetched once per host and enforced at runtime (previously only documented, never checked programmatically); `Retry-After` (seconds or HTTP-date) is honored on 429 before falling back to the existing backoff formula.
- **Daily request budget**: new `crawl_budget` table + `Store.record_request()`/`requests_used_today()`; `--max-requests-per-day` stops a run gracefully mid-crawl (resumable via the existing queue, not a hard failure).
- **Discover/enrich/update modes** (`scraper/discovery.py`, `scraper.py --mode`): `discover` creates development stubs straight from `/buildings` listing cards (name/url/status only, no per-page fetch) instead of always doing full extraction; `enrich` visits stubs and clears `is_stub`; `update` re-crawls existing rows prioritized by status (under_construction/planned first) then staleness. Plain `python scraper.py <seed>` (no `--mode`) is unchanged.
- **Area classification** (`scraper/normalizer.py::classify_area_type`): malls/landmarks (e.g. Dubai Mall, Ski Dubai) were previously stored as ordinary community rows since they share the same `/dubai/{slug}` template and prose pattern as real communities — verified prose-pattern and `dld_community_code IS NULL` heuristics would have misclassified real communities (The Springs, Arjan, etc.) before rejecting both; settled on a safe `mall` keyword regex + a small manually-verified landmark list. `Store.backfill_area_types()` reclassifies existing rows on every startup, idempotent.
- **`entity_aliases` table**: proper structure (alias, alias_type, confidence, is_manual) replacing the flat `also_known_as` string; backfilled from `also_known_as` + `dld_community_name_en` on every startup.
- **`mentioned_places` table**: internal-link place mentions (name, url, context sentence, section) extracted from the "Transport & Access" prose block (`scraper/parser.py::parse_mentioned_places`) — deliberately captures mentions only, never fabricates distances/coordinates the source doesn't structurally provide. Wired into live crawls (`discovery.py`) for both area and development pages, plus a one-time `Store.backfill_mentioned_places()` that populated 45 real rows from already-cached raw HTML with zero new network requests.
- **`--status` CLI report** (`scraper.py`): entity counts, area_type breakdown, running jobs, queue status, requests-today.
- **Dashboard panel** (`dashboard/queries.py::crawl_health`, `dashboard/templates/index.html`): requests today, most recent crawl error, mall/landmark counts, mentioned-places/alias counts — all live-queried, no hardcoded numbers.
- **Fixed a real, pre-existing dashboard bug found while verifying the new panel**: `dashboard/app.py` was calling the old Starlette `TemplateResponse(name, context)` signature; the Starlette version actually installed in this environment expects `(request, name, context)`, so `name` was silently receiving the context dict, throwing `TypeError: unhashable type: 'dict'` on every single dashboard route (not just the one touched this session). Fixed all 6 call sites to the new signature; verified all routes (`/`, `/areas`, `/areas/{id}`, `/developments`, `/developments/{id}`, `/export`) render 200 both via `TestClient` and a real browser.
- Local environment was also missing `h2` and `jinja2` (both already correctly pinned in `requirements.txt`, just not installed) — installed to get the full test suite and dashboard green; no requirements.txt changes needed.
- 155 scraper-related tests passing (`pytest tests/ -q`, excluding the unrelated analytics app's `test_analytics.py`/`test_api_smoke.py`/`test_entity_resolution.py`/`test_search_rank.py`, which need `duckdb`/`rapidfuzz` not installed in this environment — pre-existing, unrelated to this work).

### Image URL capture (added after a follow-up user request)
User wants images preserved for later compilation but not downloaded yet — so this captures URLs only, no binary downloads. Investigated real cached HTML first: a naive "grab every `<img>`" would be wrong (a Mirdif area page has 174 `<img>` tags but only ~18 are actually Mirdif's own — the rest are repeated site-wide nav thumbnails). Scoped extraction instead:
- **Hero image** (`AreaPage`/`DevelopmentPage.hero_image_url`): the one `<img alt="{exact page name}">` — verified this exact-alt-match pattern on both area and development pages.
- **Sub-community thumbnails** (`SubCommunityRef.image_url` → `sub_communities.image_url`): the `<img>` inside each sub-community's own card link, alongside its existing name/url/status.
- **Document galleries** (`DocumentRef.photo_urls` → `documents.photo_urls_json`): masterplan/construction-photos/design-stage sections use a PhotoSwipe widget whose `<a href>` IS the full-res image URL — extracted directly, reusing the same heading-matching already in place for `photo_count`.
- One-time `Store.backfill_image_urls()` populated the real DB from already-cached HTML, zero new requests: 58/60 areas, 185/185 developments, 301/301 sub-communities, 596 document rows with gallery URLs.
- **Perf fix found along the way**: `backfill_mentioned_places()` (added earlier this session) had no "already processed" marker and was re-parsing all 245 cached pages' HTML on every single `Store()` construction — a `--status` call had crept up to ~25s. Fixed by adding a `scraped_pages.mentions_backfilled` flag (and the equivalent `images_backfilled` for the new image backfill, since `hero_image_url IS NULL` alone can't distinguish "not yet tried" from "genuinely has no matching image" — 2 real rows, Angelica Residences and The Springs Souk, would have been re-parsed forever otherwise). Startup dropped back to ~0.7s after the one-time migration pass.
- Actual image *downloads* (bytes to disk) remain a deliberately separate, not-yet-built step — same Fetcher/dedup/budget pattern as raw HTML would apply whenever that's needed.
